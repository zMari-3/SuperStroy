# SuperStroy

Android-приложение на Kotlin для быстрой записи строительных дефектов и задач прямо на объекте. Пользователь фотографирует дефект, диктует название, ответственного бригадира и срок — приложение распознаёт речь, извлекает данные, автоматически добавляет дату, срок, ответственного, геопозицию и фотографию. Проект демонстрирует SOLID, Clean Architecture, Dependency Injection через Hilt, Flow, локальный кеш с офлайн-очередью и трехуровневое тестирование в реальном Android-приложении на Jetpack Compose.

## Проблема и решение

На стройке дефекты и задачи фиксируют разрозненнофиксировать не удобно: фото в галерее, текст в мессенджере, срок «в голове». Информация теряется, ответственные забываются, сроки нарушаются, повторный ввод в офисные системы дублирует работу. Руки заняты, печатать на телефоне неудобно.

Решение — цельное приложение для хранения: фото дефекта → голосовая диктовка → распознавание и извлечение полей → запись с датой, сроком, ответственным, координатами и фото. Пользователь может исправить поля вручную и сохранить запись локально, а при появлении сети — синхронизировать с сервером.

## Целевая аудитория
- Прорабы и мастера участков.
- Инженеры.
- Бригадиры и ответственные за устранение замечаний.
- Небольшие подрядные организации (5–50 человек).

## Технологический стек
- Kotlin 2.2.10 (Built-in Kotlin — встроен в AGP, отдельный плагин kotlin-android не используется)
- Android Gradle Plugin 9.4.0
- Gradle 9.6.0
- Gradle Kotlin DSL + version catalog (libs.versions.toml) — единый источник версий зависимостей
- Jetpack Compose (Material 3) для UI
- Hilt для внедрения зависимостей, KSP для генерации кода (kapt не используется — несовместим с Built-in Kotlin)
- Kotlin Coroutines & Flow для асинхронности и состояния экрана
- Room для локального кеша и очереди офлайн-синхронизации
- CameraX для съёмки фото
- FusedLocationProviderClient для геопозиции
- JUnit 4, MockK, Turbine для unit-тестов
- Compose UI Testing для UI-тестов

## Архитектура

Проект построен по правилу зависимостей чистой архитектуры: три слоя, зависимости направлены только внутрь, к центру.

- **Domain** — центральный слой. Содержит доменную модель дефекта, интерфейс репозитория и аппаратных возможностей (камера, геолокация, распознавание речи), а также use cases с реальной бизнес-логикой: создание дефекта из голосовой команды, извлечение названия/ответственного/срока из распознанного текста, загрузка списка с фильтрацией. Не зависит ни от Android SDK, ни от каких-либо внешних библиотек — чистый Kotlin.
- **Data** — реализует интерфейс репозитория, объявленный в Domain. Сюда входят Room DAO и Supabase-клиент, мапперы DTO ↔ модели, обёртки над CameraX, FusedLocationProviderClient и SpeechRecognizer. Детали происхождения данных и работы с железом скрыты от остальных слоёв; замена источника данных или способа распознавания затрагивает только этот слой.
- **Presentation** — состояние экрана, ViewModel и Compose-компоненты. ViewModel не знает про способ хранения данных и про конкретную реализацию камеры или микрофона. Compose-экран разделен на «умную» обертку (знает про ViewModel) и «глупую» часть, которая получает состояние и обработчики событий как параметры и ничего не создает сама

## Внешний источник данных и аппаратные функции

- Аппаратные функции — камера (CameraX, основная), геолокация (FusedLocationProviderClient, автоматическая метка), микрофон (голосовой ввод). Доступ к железу скрыт за интерфейсами в domain, чтобы его можно было подменить в тестах.

## Порядок реализации

Проект собирался снизу вверх, от центра архитектуры к внешним слоям — так, чтобы каждый следующий шаг опирался только на уже существующие абстракции, а не наоборот

1. Определена доменная модель дефекта  и интерфейс репозитория — контракт, который остальные слои обязаны соблюдать
2. Реализован единственный use case с настоящей бизнес-логикой —  разбор распознанного текста на название, ответственного и срок, создание дефекта, загрузка списка с фильтрацией. Операции, не содержащие отдельной логики, оставлены как прямые вызовы репозитория.
3. Написаны реализации репозитория поверх Room и Supabase, обёртки над CameraX, FusedLocationProviderClient и SpeechRecognizer, а также мапперы DTO - модели. Детали источника данных и железа скрыты от остальных слоёв.
4. Настроен Hilt: точка входа приложения, подключение экранов к графу зависимостей, модули, связывающие интерфейсы репозитория и аппаратных возможностей с их реализациями.
5. Описано состояние экрана отдельно от доменной модели (список, загрузка, ошибка, статус синхронизации) и реализованы ViewModel, управляющие созданием дефекта, списком и редактированием.
6. Собраны экраны на Jetpack Compose с разделением на компонент, работающий с ViewModel, и компонент, работающий только с переданными данными.
7. Добавлены точки входа приложения и подключение экранов, обработка разрешений камеры/геолокации/микрофона с понятными rationale-экранами.
8. Написаны тесты на всех трёх уровнях: изолированные unit-тесты use cases, unit-тесты ViewModel с подменой источника данных, UI-тесты Compose-экранов (успех + ошибка) без поднятия ViewModel.

## Тестирование

- **Unit-тесты бизнес-логики** — проверяют use case в полной изоляции, без Android-окружения и без реальных зависимостей, с использованием самостоятельно написанной подмены репозитория, камеры, геолокации и распознавания речи.
- **Unit-тесты состояния экрана** — проверяют ViewModel через тот же принцип подмены зависимостей, с подменой главного диспетчера корутин для корректной работы в тестовом окружении. Проверяются успех, ошибка сервера, таймаут, отсутствие интернета и переход в офлайн-очередь.
- **UI-тест** — проверяет реакцию Compose-интерфейса на клик пользователя, используя только «глупую» часть экрана — без поднятия ViewModel и без обращения к реальным зависимостям. На каждый экран — сценарий успеха и сценарий ошибки.
